# T-055 Run the Kiln UI without a window from a script, and read back what it shows

## Goal
Today nothing can observe a Kiln UI, so no `ui.*` item can be tested or evaluated (ADR-0008,
D-145). After this task a caller runs

```text
kiln script <script> [--root <dir> | --memory] [--log <file>] [--size <w>x<h>]
```

and gets, for each script line, one response line: control requests are answered exactly as
`kiln-cli control` answers them, in the same session the UI uses; UI requests act on the UI as a
user would (focus, click, type, key, scroll, frames) or report what the last frame shows
(snapshot). It needs no display, window system or GPU. The UI run is the **shell** this task
builds: a path field, an Open button, the list of open documents and a message line. T-056 adds
the window and the editor view to the same UI; later tasks add panels.

Gate path: `xtask/ui-allowlist.toml`, only if the director answers Q-1 with A; the approval row
must then contain `gate paths`. Independent test author (high tier).

Reading list: `docs/adr/0008-ui-observation.md` (the decision and the probe), `docs/control-protocol.md`
(framing, responses, the session log, exit codes of `run`), `docs/protocol/cli-memory-seed.md`
(order of checks, for the style), `xtask/ui-allowlist.toml`, `xtask/layers.toml`
(`headless_forbidden`), CHARTER §3 (L5, decision 1).

## Interface

### Command line
- `kiln script <script> [--root <dir> | --memory] [--log <file>] [--size <w>x<h>]`
  - `<script>`, `--log <file>`: paths on the host, relative to the current directory.
  - `--root <dir>` (default: the current directory) and `--memory` (an empty in-memory file
    system) as for `kiln-cli run`; they exclude each other. A bad root is refused before any
    request runs, as `kiln-cli` refuses it (stderr message naming the root as given, nothing on
    stdout, exit 2).
  - `--size <w>x<h>`: the UI's size in points, integers 200 to 8192 each; default `1280x800`.
  - Options before or after the positional argument, each at most once.
- `kiln --help`, `kiln -h`, `kiln script --help`: usage on stdout, exit 0.
- Exit codes of `kiln script`: 0 every response `ok:true`; 3 at least one `ok:false`; 2 usage
  error, unreadable script, bad root, log file not writable (message on stderr, nothing on
  stdout); 1 writing stdout failed. `kiln` with no subcommand keeps its current behaviour in this
  task (T-056 replaces it with the window).

### Script lines
Framing as `docs/control-protocol.md` "Framing": one request per line, blank lines get no
response, one compact response line with sorted keys per other line, in order; the session
continues after any failure. A line that does not parse, is not an object, or has an invalid
`id` gets the control protocol's error for it.

- An object **with** a key `ui` is a **UI request**. Allowed keys: `id`, `ui` and those of its
  action below; any other key is refused (`bad_request`).
- Every other object is a **control request**: its response is the line `kiln-cli control`
  would write for it at this point of the same session (same bytes).

### UI requests
Targets: `target` is an object with one or more of `role`, `label`, `label_contains`, `value`,
`value_contains` (strings); a node matches when every given field matches (`role`, `label`,
`value` exactly; `*_contains` as a substring). Offscreen nodes match too.

| `ui` | Other keys | Does |
|---|---|---|
| `snapshot` | — | reports the last frame (below); runs no frame |
| `frames` | `count` (integer 1–600) | runs exactly `count` frames with no input |
| `focus` | `target` | gives the target keyboard focus |
| `click` | `target`; `button` (`"primary"` default, `"secondary"`); `modifiers` (array of `"ctrl"`, `"shift"`, `"alt"`, `"command"`; default none); `at` (optional `{"row":r,"col":c}`, integers ≥ 0) | a pointer press and release at the target, as a user's click: at its centre, or with `at`, at the left edge of char `c` of the target's painted row `r` (its `rows`, below), or just right of the row's last char when `c` equals the row's length |
| `type` | `text` (string) | the text as typed input to the focused node |
| `key` | `key` (a name from the table in `docs/protocol/ui.md`); `modifiers` as for `click` | one key press and release |
| `scroll` | `target`; `direction` (`"up"`, `"down"`, `"left"`, `"right"`); `steps` (integer 1–100, default 1) | scrolls the scrollable area that contains the target by `steps` steps |

Key names (at least): `A`–`Z`, `0`–`9`, `Enter`, `Tab`, `Backspace`, `Delete`, `Escape`,
`Space`, `ArrowLeft`, `ArrowRight`, `ArrowUp`, `ArrowDown`, `Home`, `End`, `PageUp`, `PageDown`,
`F1`–`F12`.

Responses: an action (`frames`, `focus`, `click`, `type`, `key`, `scroll`) answers
`{"id":…,"ok":true,"result":{"frames":<n>,"settled":<bool>}}`: after the input the runner runs
frames until the UI asks for no further frame or 60 frames ran (`frames` runs exactly `count`);
`n` is the number run and `settled` is true when the UI asked for no further frame. Before the
first request of a script the runner runs frames the same way.

`snapshot` answers `{"id":…,"ok":true,"result":{"frames":<total frames run in the session>,"root":<node>}}`.
A node is an object with:
- `role`: the accessibility role the toolkit reports for it, in snake_case (`button`, `label`,
  `text_input`, `window`, …);
- `label`, `value`: strings, each present only when the node has one;
- `focused`, `disabled`, `offscreen`: `true`, present only when true (`offscreen`: no part of the
  node lies in the visible part of the window);
- `selected`, `toggled`: booleans, present only when the node has that state;
- `selection`: `{"anchor":a,"head":h}` in chars of `value`, present for a text input that has a
  caret or selection;
- `rows`: for a node that shows text: the text the frame painted inside the node and inside the
  visible part of the window, one array per painted row from top to bottom, each row a list of
  runs `{"text":…,"color":"#rrggbb"}` from left to right, adjacent runs of the same colour merged;
- `children`: the child nodes in the toolkit's order (always present, possibly empty).

Nodes that the frame does not show at all (hidden) are left out. The snapshot is computed from
what the toolkit produced for the frame (its accessibility output and painted shapes), never from
a description the UI code writes about itself (ADR-0008 decision 2).

UI refusals: `{"error":{"code":"ui","kind":<kind>,"message":…},"id":…,"ok":false}`, checked in
this order: `bad_request` (a missing, unknown or wrongly typed key, a number out of range, an
unknown key or modifier name, an empty target), `unknown_action` (`ui` is not one of the table),
`no_target` (no node matches), `ambiguous_target` (more than one node matches),
`not_actionable` (the action cannot apply: `focus` or `type` with no node that takes text input,
`scroll` with no scrollable area around the target, `at` on a target without `rows` or beyond
its painted rows or a row's length). A refused UI request runs no frame and
changes nothing. Message caps as in the control protocol (200 chars). This task adds **no
registry command** (so ADR-0006's declarations are unaffected).

### The shell (what this task's UI shows)
- a text input labelled `Path` (role `text_input`);
- a button labelled `Open`;
- a node labelled `Documents` whose children are one node per open document, in id order, each
  with the document's path as its `value`;
- a node labelled `Message` whose `value` is empty, or, after a refused open, begins with the
  refusal's `kind` (e.g. `not_found`) followed by free text.
Clicking `Open` (or `Enter` in `Path`) asks the session to open the path in `Path`. Every
interactive node has a non-empty `label`.

## Pinned
- (a) Errors and precedence: line-level errors exactly as the control protocol (`invalid_json`
  / `not_utf8`, `syntax`; `invalid_request` / `not_an_object`, `bad_id`) before anything else;
  then the UI order above (`bad_request` → `unknown_action` → `no_target` → `ambiguous_target`
  → `not_actionable`). Control requests: unchanged kinds (`error_kinds` in `docs/commands.json`).
  A UI refusal and a refused control request leave the session and the UI unchanged and are not
  logged.
- (b) Files: reads `<script>` once, whole, at start; writes `--log <file>` (created or truncated
  before the first request, written after the last, the format of "The session log as a
  script"); touches the root only through control requests (the UI's included). No other file is
  written; nothing is read from or written to the user's configuration or home directory.
- (c) Order of checks at start: usage (options, `--size` range) → script readable → root (or
  `--memory`) → log file writable → requests. Same message and exit-code conventions as
  `kiln-cli run` (`docs/control-protocol.md`, `kiln-cli` and exit codes).
- (d) Paths: script and log relative to the current directory; request paths relative to the
  root, as in the control protocol. Platform: Linux is what the gate and this spec's evidence
  cover. No display variable is read in script mode.
- (e) Threat model: a script is trusted as much as a `kiln-cli run` script and no more. The UI
  must not widen what a session reaches: every file it reads or writes goes through a control
  request (confinement and refusals as `docs/protocol/paths.md`). The runner spawns no process,
  opens no network connection, reads no clock for behaviour. Hostile scripts: huge lines are
  read whole (as the control protocol states); `frames` and `scroll` are capped (600, 100) and
  each action's settling is capped at 60 frames, so one request runs a bounded number of frames;
  deep or wide UI trees are the UI's own (no script controls their size beyond opening
  documents).
- (f) Tests that pin what this changes: none on main (`apps/kiln` has no tests; no scorecard
  item names a `kiln` test). Not to be pinned by this task's tests (golden rule 9): a whole
  snapshot, the set of roles, the node tree's shape beyond the shell nodes named above (T-056 and
  every module add nodes), any message text, the key-name table beyond the listed minimum, the
  usage text.
- (g) Worked examples. Control parts executed with the `kiln-cli` binary of this main (R-225):
  a root `proj/` with `src/a.rs` = `fn main() {\n    let x = 1;\n}\n`:
  ```text
  {"id":1,"command":"doc.list"}
  → {"id":1,"ok":true,"result":{"docs":[]}}
  {"id":2,"command":"doc.open","params":{"path":"src/a.rs"}}
  → {"id":2,"ok":true,"result":{"already_open":false,"doc":1,"encoding":"utf-8","len_chars":29,"line_ending":"lf","mixed_line_endings":false,"path":"src/a.rs"}}
  {"id":3,"command":"doc.open","params":{"path":"src/missing.rs"}}
  → {"error":{"code":"rejected","kind":"not_found","message":"cannot open src/missing.rs: not found"},"id":3,"ok":false}
  {"id":4,"command":"doc.list"}
  → {"id":4,"ok":true,"result":{"docs":[{"dirty":false,"doc":1,"path":"src/a.rs"}]}}
  ```
  (`kiln-cli run s.jsonl --root proj --log l.jsonl` exits 3; the log holds requests 1, 2 and 4,
  renumbered 1–3.) The same four lines through `kiln script s.jsonl --root proj` must print the
  same four lines and exit 3 (AC-1). UI parts (not executable before the implementation;
  expected by the definitions above): on a fresh session over `proj/`,
  `{"id":"f","ui":"focus","target":{"label":"Path"}}`, `{"id":"t","ui":"type","text":"src/a.rs"}`,
  `{"id":"c","ui":"click","target":{"label":"Open"}}` each answer `ok:true`; a following
  snapshot has, under the node labelled `Documents`, one child with `value` `src/a.rs`;
  `{"command":"doc.list"}` then lists `src/a.rs` as doc 1; the log holds a `doc.open` with
  `{"path":"src/a.rs"}`. Typing `src/missing.rs` and clicking `Open` instead leaves `Documents`
  without children and gives `Message` a value beginning `not_found`.
- (h) Evaluator calls: no scorecard item. The evaluator uses `kiln script` from T-056 on (ADR-0008).
- (i) Sentences for `docs/protocol/ui.md`, worded for copying, with their evidence:
  - S1 "`kiln script` needs no display, window system or GPU." Evidence: ADR-0008 probe b1–b3
    (egui frames, painted text and the accessibility tree read without a display); AC-9 for Kiln.
  - S2 "A control request in a script gets the response line `kiln-cli control` would give it
    at the same point of the same session." Evidence: AC-1.
  - S3 "Every change the UI makes to documents or files is a control request: it is in the
    session log, and running the log with `kiln-cli run` on a copy of the initial files gives the
    same files." Evidence: AC-3.
  - S4 "The UI sends no request while no input arrives: `frames` on an idle UI adds nothing to
    the session log." Evidence: AC-5.
  - S5 "The output and the log depend only on the script, the initial files and the build: the
    same script on two copies of the same directory, at different locations, prints the same
    bytes and writes the same log. No clock is read; each frame advances the UI's time by exactly
    1/60 s." Evidence: ADR-0008 probe b5 (toolkit level, identical digests across processes);
    AC-6 for Kiln.
  - S6 "After an action the runner runs frames until the UI asks for no further frame, at most
    60, and reports how many it ran and whether it settled." The cap is a stated limit; the
    number of frames the shell needs to settle is **to be measured by the implementer** (log the
    largest count seen in the acceptance scripts). Toolkit evidence: in the probe each
    egui_kittest `run()` settled within its default of 4 steps (ADR-0008 b3).
  - S7 "A refused UI request runs no frame and changes nothing." Evidence: AC-7.
  - Limits, copied: a script line is read whole into memory (as the control protocol); mouse-wheel
    input is not offered (ADR-0008 b4: wheel events did not scroll in the probe; `scroll` uses
    the accessibility scroll action).

## Acceptance criteria
All through the built `kiln` binary (`CARGO_BIN_EXE_kiln`), with temporary roots and every
spawned process under a timeout. Nodes are found by role, label or value, never by a whole
snapshot.
- AC-1 (control pass-through): for scripts made only of control requests (the worked example,
  the control protocol's worked example, and random sequences of `doc.*`, `cursor.*`, `search.*`,
  `syntax.*`, `project.tree` requests over a small project, malformed lines included), `kiln
  script` prints exactly the lines `kiln_control::Host` gives for the same lines on a copy of the
  same root, exits with the code `kiln-cli run` documents for those responses, and `--log`
  writes exactly `Host::log_script()`. Oracle: `Host` (differential).
- AC-2 (shell shown): a snapshot of a fresh session has a `text_input` labelled `Path`, a
  `button` labelled `Open`, a node labelled `Documents` with no children and a node labelled
  `Message` with an empty or absent value; after a control `doc.open` of `src/a.rs` and of
  `b.txt`, `Documents` has two children with values `src/a.rs`, `b.txt` in that order. Oracle:
  `doc.list` in the same session.
- AC-3 (the UI dispatches): `focus` `Path`, `type` a path, `click` `Open` opens the file: the
  next snapshot lists it under `Documents`, `doc.list` lists it, and the log has a `doc.open`
  with that path; `Enter` instead of the click does the same. Running the log with `Host` (or
  `kiln-cli run`) on a copy of the initial root gives the same `doc.list` and the same files.
  Oracle: registry state, log replay.
- AC-4 (refusals shown): opening through the UI a missing path, a directory, a path through a
  symlink that leads outside the root, and `../x` leaves `Documents` unchanged and gives
  `Message` a value beginning with the kind a control `doc.open` of the same path reports
  (`not_found`, `not_a_file`, `outside_root`, `invalid_path`); no `doc.open` is in the log for
  them. Oracle: the same request as a control request in a second session (differential).
- AC-5 (idle): `{"ui":"frames","count":600}` on an idle shell adds nothing to the log (compare
  `--log` with and without that line) and the snapshots before and after are equal. Oracle:
  log comparison.
- AC-6 (determinism): one script mixing every UI action and control requests, run on two copies
  of the same root at different paths, and run twice while the machine is loaded by other
  processes, prints byte-identical stdout and writes byte-identical logs. Oracle: byte equality.
- AC-7 (UI refusals): one script provokes each kind (`bad_request` for an unknown key, a missing
  `target`, `count` 0 and 601, an unknown modifier; `unknown_action`; `no_target`;
  `ambiguous_target` with a target matching two nodes, e.g. `{"value_contains":"."}` with two
  documents open; `not_actionable` for `type` with nothing focused and for `click` with `at` beyond the target's
painted rows): each answers `ok:false`,
  code `ui` and that kind; a snapshot and `--log` show nothing changed; the exit code is 3; the
  precedence of (a) holds for a request that has two faults (e.g. an unknown key and an unknown
  action → `bad_request`). Oracle: exact kinds; snapshot and log equality.
- AC-8 (command line): usage errors (unknown option, two of `--root`/`--memory`, `--size` out of
  range or malformed, missing script) exit 2 with nothing on stdout; an unreadable script, a bad
  root and an unwritable log exit 2; `--help` exits 0 with the usage on stdout. Oracle: exit
  codes and empty stdout (no message text).
- AC-9 (no display): AC-2's script with `DISPLAY` and `WAYLAND_DISPLAY` removed from the
  environment answers the same lines. Oracle: equality.
- AC-10 (accessible names): in every snapshot taken by AC-2 to AC-7, every node with role
  `button` or `text_input` has a non-empty `label`. Oracle: tree walk.

### Rulings after the first join (director, D-149; the implementer's questions 1 to 8 of R-226; told to both builders)
The first join failed one acceptance test of 18, `ac6_frame_counts_add_up` (21 frames between two snapshots against
20 reported), on the implementer's question 1.
- **n4 (question 1).** A control request runs no frame, and a `snapshot` runs none: a snapshot reports the last
  frame. What a control request changed in the session is shown from the next frame on, so a script that wants to
  see it runs a frame first (`{"ui":"frames","count":1}` or any action). Between two snapshots the session's frame
  total grows by exactly the frames the UI requests between them reported. The implementer removes the unreported
  frames; `docs/protocol/ui.md` says this in one sentence. The test author checks that no test takes a snapshot
  right after a control request and expects its effect without a frame in between (AC-2's wording allows a frame).
- **n5 (question 2).** A node that shows text reports the text in its own `value`, `rows` and `selection`; the
  toolkit's per-row child nodes are not reported as nodes. Accepted.
- **n6 (question 3).** Every scrollable area is reported as a node of role `scroll_view` whose bounds are the
  visible part. Accepted; `docs/protocol/ui.md` states it, and later UI tasks report scroll areas the same way.
- **n7 (question 4).** `focus` on a node that does not take text input is refused `not_actionable`. Confirmed.
- **n8 (question 5).** A `click` whose target is `offscreen` is refused `not_actionable` and changes nothing: a user
  cannot click what is not visible; the script scrolls first. (The implementer had it delivered and answered ok.)
  The test author adds a case if this task's shell can show an offscreen node (enough open documents to overflow
  `Documents`); if it cannot, it says so and the implementer's unit test and the reviewer cover it.
- **n9 (question 6).** AC-5's "equal snapshots" means equal `root`; the `frames` totals differ by the frames run.
- **n10 (question 7).** `serde_json` as a direct dependency of `kiln-ui` and a dev-dependency of `apps/kiln` is
  accepted (already a workspace dependency; the lock does not change by it).
- **n11 (question 8).** Painted text belongs to the deepest node whose rectangle contains the centre of each char,
  and a space takes the colour of its neighbour. Accepted as the published rule; `docs/protocol/ui.md` states it
  with that limit.
