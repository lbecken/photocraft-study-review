# T-037 Check the root and the path's location when `doc.open` names a path that is already open

## Goal
Today `doc.open` of a path that is already open in the session returns the open document with
`already_open: true` and checks nothing. It does so even when the path now leads outside the
root, or the root has been replaced or has vanished (VERIFIED: `crates/kiln-commands/src/doc.rs`
:172–178 on `task/T-036` `cbcfdbb`, identical to main, looks the path up among the open
documents and returns before any file-system call; reproduced by the evaluator,
`evaluations/iter-1.md` NEW-1, by both T-036 builders (D-117), by T-036's reviewer
(`reviews/T-036-r1.md` on `task/T-036`, "Sentences left untrue until T-037"), and by the probes
of Pinned (g)). `docs/protocol/paths.md` (T-036's text) says at :51–53 "At open and at save …
A path whose location is outside the root is refused", and at :21–24 that once the root path
stops leading to the root "the session refuses every path with `outside_root`, at open and at
save". The document and the binary disagree.

After this task (director's ruling D-092, option O1) a re-open applies the check of the root and
the check of the path's location, and nothing more: a path whose location is now outside the
root, or a session whose root path no longer leads to its root, is refused with `outside_root`;
a location that cannot be shown to be inside the root is refused with `io_error`. A re-open
still does not require the file to exist, to be a regular file, to be readable or to decode,
and it reads nothing. `paths.md` and `doc.open`'s description say exactly this, and tests pin
the behaviour.

No gate path and no dependency in `touches`. Tier high by ADR-0002: the confinement boundary
that `docs/protocol/paths.md` states. One scorecard item, one behaviour: not a bundle (D-091;
see "Spec check R-196").

## Definitions
- **Root, location, inside, the walk**: as `docs/protocol/paths.md` "The root" and "Location".
- **U** (the identity of unprivileged cases): as T-036 Definitions. When the test process runs
  as uid 0, the `kiln-cli` child runs as uid 65534 and gid 65534 (`CommandExt::uid`/`gid`), on
  a fixture given to that identity (`lchown`); otherwise the child runs as the test's own
  identity. A case that needs U never skips: if the identity can bypass permissions (the
  negative control below), the test fails.
- **Open path**: the path of a document open in the session. A request path *is already open*
  iff, after the lexical check, it is equal as a string to the path of an open document
  (VERIFIED: `doc.rs`:172–176 compares `RelPath` values, which hold the path as given,
  `crates/kiln-workspace/src/path.rs`:7–8). So the key is the path text, not the file: in a root
  holding `l -> a.txt`, opening `a.txt` and then `l` gives two documents (VERIFIED by probe,
  R-154). This task does not change the key.
- **Re-open**: a `doc.open` whose path is already open.
- **Location check**: the root-identity check (`DiskFs::current_root`, `disk.rs`:207–216 on
  `cbcfdbb`) followed by the walk of the path to its location (`locate`/`locate_steps`,
  :220–329), exactly as `read` and `write_atomic` perform them before they look at what is at
  the location. Its outcome is one of: the location is inside the root, whatever is or is not
  there (a regular file, a directory, a FIFO or other special file, nothing, or a component
  before the last that is missing or not a directory); `OutsideRoot` (the root path no longer
  leads to the root directory, or the location is outside, or the walk failed once outside);
  or `Io` (the walk failed inside the root: more than 40 symlinks, or a directory on the way,
  the root included, that the process may not search).

## Interface
`doc.open` params and result are unchanged. No new kind and no `reason.rs` row: the re-open
uses the kinds `outside_root` and `io_error`, which `doc.open` already reports.

1. **Re-open on a disk session.** A `doc.open` whose path is already open, in a session on the
   disk file system (`kiln-cli run`, `exec` or `control` with `--root` or the default root,
   `Host::on_disk`, `Context::with_vfs(Box::new(DiskFs::new(…)?))`):
   - performs the location check of the path, once, and nothing else; it opens, reads,
     creates or changes no file (only `lstat` and `readlink` of entries on the path, and the
     resolution of the root path, are made);
   - is refused with `rejected` / `outside_root` if the outcome is `OutsideRoot`;
   - is refused with `rejected` / `io_error` if the outcome is `Io`;
   - otherwise returns `{"already_open": true, "doc": <id>, …}` exactly as today: the open
     document's id, path, encoding, its current text's line endings and length.
   `exec` runs one request in a fresh session, so a re-open cannot occur there.
2. **A refused re-open leaves the session as it was**: the document stays open with the same
   id, text, dirty flag, undo/redo history and selection; `doc.list` is unchanged; nothing is
   added to the session log (as for every refused request). Once the path leads inside the
   root again (for example the root moved back), the re-open answers `already_open: true`
   again.
3. **Re-open on an in-memory session** (`kiln-cli run`/`exec` with `--memory` or
   `--memory-seed`, `Context::new`, `Host::in_memory`): unchanged, always
   `already_open: true`. (`kiln-cli control` accepts only `--root`, VERIFIED: probe R-196,
   "unknown option `--memory-seed` for `control`".)
4. **First open** (a path that is not open): unchanged in every respect.
5. **Rust API.** `kiln_workspace::Vfs` gains one **required** method (no default body, so no
   implementation can skip the check silently; T-019 added `list_dir` the same way):
   ```rust
   /// The location check of `path` (`docs/protocol/paths.md`, "The root" and "Location"):
   /// `Ok(())` iff the root is still the root and the location of `path` is inside it,
   /// whatever is or is not there. Errors: `OutsideRoot`, then `Io` (the walk failed inside the
   /// root), as for `read`. Opens, reads, creates and removes nothing.
   fn check_location(&self, path: &RelPath) -> Result<(), VfsError>;
   ```
   `DiskFs` implements it with `locate` (`Ok` for every `Found`); `MemoryFs` returns `Ok(())`
   (it has no root identity and no links). The only implementations are these two (VERIFIED:
   `git grep 'Vfs for'` on `cbcfdbb` finds `disk.rs`:448 and `memory.rs`:58 only). No other
   public signature changes; the acceptance tests do not call it (they go through `doc.open`).
   No existing method can serve: `is_file` answers `false` for "outside" and for "missing"
   alike (`vfs.rs`:101–103); `read` reads the file; `list_dir` (T-019) opens and reads a
   directory at the location and answers `NotFound`/`NotAFile` for other entries (`disk.rs`
   :473–523), and `Io` for a directory it cannot read, which O1 answers ok.
   `doc.open` maps the error exactly as a first open does (`OpenError::Vfs(e)`, its `Display`,
   and `RejectReason::from(&OpenError)`), so the messages are `cannot open <path>: resolves
   outside the root` and `cannot open <path>: I/O error: <description>` (not pinned by tests).

### Order of checks for `doc.open`
`invalid_params` (schema) → `invalid_path` (lexical) → is the path already open?
- yes → location check (`outside_root`, then `io_error`) → `already_open: true`;
- no → as today (paths.md "The rule": `outside_root`, `not_found`, `not_a_file`, `io_error`,
  then `decode_error`).

## Threat model
Kept from T-008 (e) and T-036: an honest user or a hostile repository; another process may
change the tree between two requests, not during one.
- **Covered.** Between two requests, the file, a directory on its path, the root or a
  directory above the root is replaced so that the open path leads outside or the root path
  leads elsewhere or nowhere: the re-open is refused, nothing is read anywhere, and the
  document stays as it was. A path whose walk fails inside the root is refused `io_error`.
- **Not covered (accepted, documented).** Changes during one request (T-008 D-3); hard links;
  a root replaced by a directory on another device with the same inode number (T-036 TG-2);
  `MemoryFs` (no links, no root).
- **What a re-open reveals.** As for a first open: whether the location is inside or outside,
  and, through `io_error`, that the walk failed inside. Nothing about the content of an outside
  file, and no host path in any message.
- **Reviewer probes adversarially:** re-open after each row of the Options table, through
  `run` and `control` (and `exec`, where a re-open cannot occur); chains that leave and come
  back; a parent directory swapped for a link outside; the root renamed away and moved back;
  a FIFO at the path (no blocking); a re-open interleaved with saves of the same document; the
  unprivileged rows as U.
