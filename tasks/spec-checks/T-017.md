# Spec check T-017 (R-067)

## Verdict: `ready after the listed edits`

The contract is sound and small. `regex =1.13.1` is already locked, and adding it changes no
package version. Every worked example in Pinned (g) reproduces exactly. The case-folding
predicate the test model uses agrees with the engine on the whole AC-1 alphabet against every
Unicode scalar value. Every pathological pattern in Pinned (e) answers or errors well inside
5 s in a debug build.

One thing stops it as written:
- **Blocker 1.** AC-1's random patterns may put a quantifier on a sub-pattern that can match
  the empty string, such as `(a*)*`, `(|a)+`, `(^)*` or `( *.??)+`. There the `regex` crate's
  results (its NFA drops a path that revisits a state at the same position) differ from a
  textbook backtracker. The spec does not pin those semantics. I wrote a naive backtracker of
  exactly the spec's subset and ran it against `regex` 1.13.1 on 20,000 random pairs:
  - **0 differences** when no quantifier has an operand that can match empty;
  - **91 differences** when such operands are allowed.

  A test author who follows the spec literally writes a test that fails against a correct
  implementation.

The fix is a restriction on the generator plus pinned wording, so there is no need to re-spec.

## 2. Unambiguous?

**2. blocker — AC-1's model disagrees with `regex` on quantified empty-matching operands.**

AC-1 allows `*`, `+`, `?` and their lazy forms on any atom, including groups and alternations
that can match empty, plus `^` and `$` (T-017:106–110). On those inputs the engine's results
come from its Thompson NFA: `e*` with a nullable `e` is compiled as `(?:e+)?`, and a path that
re-enters a state at the same position dies. The spec does not describe that, and a textbook
backtracker does not reproduce it.

Results from `regex` 1.13.1 (VERIFIED, char offsets, group 1 shown second):

| Pattern | Text | `regex` | A textbook backtracker |
|---|---|---|---|
| `(?:a\|())*` | `aa` | `0..2`, group 1 = None | group 1 = `2..2` |
| `(\|a)+` | `aa` | `0..0`, `1..1`, `2..2` (each group = same) | `0..2` |
| `( *.??)+` | ` k0σb0ks` | `0..1` then empty matches at 2…8 | `0..8` |
| `(^)*` | `éS` | at 0 group `0..0` | at 0 group None |
| `(a*)*` | `b` | `0..0` with group `0..0` | depends on the model's empty-loop rule |

Differential run: Python model of the spec's subset against the engine. 20,000 pairs, half of
them case-insensitive, texts of 0–10 chars over the AC-1 alphabet, patterns of depth ≤ 3.
- With operands of quantifiers restricted to sub-patterns that cannot match empty: **0
  differences** (and 0 regex compile errors).
- Without the restriction: **91 differences**.

*Edit (AC-1), add:* "The generator never applies `*`, `+`, `?` or a lazy form to a sub-pattern
that can match the empty string: `^`, `$`, a group or alternation with a branch that can be
empty, or anything already quantified with `*`/`?`. On such patterns `find_all` follows the
engine, documented by these worked examples (add the table above to Pinned (g)), and is not
modelled."

Also pin the capture rule the model needs: "A group inside a repetition holds its range from
the last iteration in which it took part. It is not reset when an enclosing repetition
iterates again." VERIFIED: `(?:(a)|b)*` on `ab` gives group 1 = `0..1`; `((a)|b)+` on `ab`
gives group 2 = `0..1`; `(?:(a)|(b))+` on `ab` gives both groups set.

T-021 AC-2 needs the same restriction (finding 14).

**3. ambiguity — what happens after an empty match is discarded.**

"An empty match at the position where the previous match ended is not reported. After an empty
match the search resumes one char later" (T-017:73–75). This admits two models:
- (a) discard the match and restart the search at `e+1`;
- (b) look for another, non-empty match starting at `e`.

The engine does (a). VERIFIED: `b|(?:)|a` on `ba` gives `0..1`, `2..2`, so `a` at `1..2` is
never reported. A backtracker that "rejects the empty match and backtracks" finds `1..2`.

*Edit (T-017:73–75):* "If the leftmost-first match found from `e` is empty and starts at `e`,
the previous match's end, it is discarded and the search restarts at `e+1`. No other match
starting at `e` is tried. Anchors and `\b` still see the whole text. After a reported empty
match at `s`, the search resumes at `s+1`." Add `b|(?:)|a` on `ba` → `0..1`, `2..2` to
Pinned (g).

**4. ambiguity — the expansion rule differs from `regex`'s own on braces and digit-led names.**

The AC-2 template alphabet (`$ { } 0 1 9 a w _ x !`) generates these cases constantly. On
`(?<w>a)(b)?` matched on `ac`, regex 1.13.1 `Captures::expand` gives (VERIFIED):

| Template | regex 1.13.1 | Spec as written (T-017:76–79) |
|---|---|---|
| `${}` | `` (empty) | no name ⇒ "other `$`" ⇒ `${}` literally |
| `${a!}` | `` | `a!` is not `[0-9A-Za-z_]` ⇒ literal `${a!}` |
| `${1 }` | `` | literal `${1 }` |
| `${ab` (no `}`) | `${ab` | literal ✓ |
| `$12x` | `` (name `12x`) | `$12` then `x`, or name `12x`: unclear |
| `$1a` | `` | unclear in the same way |
| `$99999999999999999999` | `` | ✓ (no such group) |
| `${0}`, `$0` | `a` | ✓ |
| `$`, `$!` | `$`, `$!` | ✓ |

The implementer cannot call `regex::Captures::expand`, because `kiln_search::Captures` holds
char offsets. Implementer and test author both write the rule by hand, so it must be exact.

*Edit (replace T-017:76–79):* "Expansion scans left to right:
- `$$` → `$`.
- `${` up to the next `}` → a reference whose name is everything between them, any chars,
  possibly empty. With no `}` later in the template, `$` is literal.
- Otherwise `$` followed by the longest non-empty run of `[0-9A-Za-z_]` → a reference with that
  name. With an empty run, `$` is literal.
- A reference whose name is all ASCII digits and parses as `usize` is a group number; otherwise
  it is a group name.
- A reference to a group that does not exist or did not take part → nothing.

This is regex 1.13.1's `Captures::expand`." Add the table above to Pinned (g).

**5. ambiguity — `expand` with captures that do not fit `text` or the pattern.**

AC-2 uses "random captures" (T-017:114). The spec does not say what happens when:
- `caps.groups.len() != group_count() + 1`;
- a range ends beyond `text`'s char length;
- `start > end`.

`CharMatch` documents `start <= end`, but its fields are public. "No panic on any pattern or
text" (T-017:84) does not cover `caps`.

*Edit:* "A group index ≥ `caps.groups.len()`, or a range with `start > end` or `end >
text.chars().count()`, expands to nothing. `expand` never panics."

**6. ambiguity — truncating `PatternError` messages.**

"The crate's message, at most 200 chars" (T-017:80–81) does not say how. The engine's messages
are multi-line and quote the pattern, so a long invalid pattern exceeds 200 chars. The control
protocol already has a rule (docs/control-protocol.md:66–69: first 199 chars, then `…`, never
splitting a char).

*Edit:* "`message` is the engine's `Display`. If it is longer than 200 chars, it is cut to its
first 199 chars followed by `…` (as the control protocol cuts details)."

**7. ambiguity — inline flags.**

"Syntax … those of the `regex` crate" (T-017:65) admits `(?-m)`, `(?-R)`, `(?s)`, `(?x)`,
`(?i)` and `(?-u)` inside the pattern. These override the line model and the options; `(?s)`
makes `.` match `\r` and `\n`. T-021 exposes patterns to users. Unpinned, one implementer
passes them through and another rejects them.

*Edit:* "Inline flags are accepted and override the options for their scope, as in the crate.
`docs/protocol/search.md` (T-021) says so." Or: "a pattern containing `(?` followed by a flag
letter gives `PatternError`".

**8. ambiguity — derives on `Regex`, and the alphabet's `K`.**
- `Regex` has no derives listed. T-021's `CompiledQuery` holds one, T-022's `FindState` keeps
  previews, and T-015 states derive `Debug`. *Edit:* `#[derive(Clone, Debug)] pub struct Regex
  { /* engine, group names */ }`.
- The AC-1 alphabet lists `K k` (T-017:109–110) while the semantics text names U+212A
  (T-017:70). *Edit:* "`K` (U+004B), `k`, and `K` (U+212A)". The predicate holds with or without
  it (VERIFIED).

**9. ambiguity — case-insensitive classes in the model.**

AC-1 states the char predicate but not how it applies to `[…]` ranges and to negation. The
engine folds the class first and negates afterwards, so `(?i)[^a]` excludes `A`.

*Edit (AC-1):* "Case-insensitively, `[…]` matches `c` iff some member `m` of the class
satisfies the predicate with `c`, and `[^…]` matches iff no member does." My model did exactly
this, with 0 differences.
