## The Windows code, read against documented Windows semantics (all "read, not run" unless the CI record shows it)
- **How the root is held.** `same_file::Handle::from_path` → `winapi_util::Handle::from_path_any` (`winapi-util-0.1.11/src/win.rs:66-76`):
  `OpenOptions::new().read(true).custom_flags(FILE_FLAG_BACKUP_SEMANTICS)` — std's defaults add share mode
  `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE` (`std/src/sys/fs/windows.rs:206`) and no
  `FILE_FLAG_OPEN_REPARSE_POINT` (only `create_new` adds it, `:333`), so the open follows links and junctions, and
  holding it does not stop others from renaming or deleting the directory as far as sharing goes. The `DiskFs` keeps the
  `Handle` (it owns the `File`) for its whole life: **held, as on Unix**. Run 44268710587 measured it: renaming the held
  root itself succeeds; renaming its parent is refused, `PermissionDenied, raw OS error Some(5)` (CI record, "MEASURED").
- **What `==` compares.** `Key { volume: dwVolumeSerialNumber as u64, index: nFileIndexHigh<<32 | nFileIndexLow }` from
  `GetFileInformationByHandle` (`winapi-util-0.1.11/src/file.rs:20-29,100-122`; `same-file-1.0.6/src/win.rs` `from_info`,
  `PartialEq`). On NTFS the file index is the MFT reference with a sequence number that changes on reuse, and the root is
  held anyway, so the Unix inode-reuse case is defended twice. On ReFS (Dev Drive) the 64-bit index is documented as not
  unique (same-file's own comment says so and notes `FILE_ID_INFO`), and the volume serial is 32 bits: two directories
  can compare equal — the **unsafe** direction (finding 2). A failing `GetFileInformationByHandle` makes `from_path` an
  `Err`: in `new` the root is refused (`Io`, `(root)`), in `current_root` `is_ok_and` gives false → `OutsideRoot`: the
  **safe** direction (but untested: finding 5).
- **`current_root`.** `fs::canonicalize` (`windows.rs:1593-1601`: opens with access 0 and `FILE_FLAG_BACKUP_SEMANTICS`,
  follows links and junctions, returns the `\\?\` final path); `fs::symlink_metadata` of that final path (not a reparse
  point); then a second open by `Handle::from_path`. A junction or symlink given as `--root` therefore makes its target the
  root and a retarget makes every call `OutsideRoot` — the Unix behaviour, nothing less safe, and **no Windows-specific
  refusal is added**, as Interface (2) says and as the module doc states. TOCTOU: a swap between `canonicalize` and
  `from_path` yields another directory's handle → `OutsideRoot`; a swap after the check is the race the module doc
  already states for Unix. One difference: `from_path` needs `GENERIC_READ` (list) on every call, `canonicalize` and
  Unix's `symlink_metadata` need none, so on Windows a root whose list right is removed during a session becomes
  `OutsideRoot`, on Unix it goes on (finding 5).
- **The temporary file.** `create_new(true)` → `CREATE_NEW` plus `FILE_FLAG_OPEN_REPARSE_POINT` (`windows.rs:333`):
  exclusive, does not follow a link at the name, `ERROR_FILE_EXISTS` → `AlreadyExists` → next name (CI: the lib's
  `all_temp_names_taken…` and `guard_t073`'s `acw2_save_creates_temp_exclusively` ok). No mode: the file gets the
  directory's inheritable ACEs; `fill_temp`'s `set_permissions` writes the target's attribute word through
  `FILE_BASIC_INFO` (`windows.rs:774-783`), not its ACL — so the result has the directory's inherited ACL, not the
  target's, and the temp file is not "owner-only" while written (finding 3). A read-only target is refused by Kiln's own
  open for writing (`write_atomic_with`, `Found::File`: `CreateFileW(GENERIC_WRITE)` on a read-only file →
  `ERROR_ACCESS_DENIED` → `PermissionDenied`), before any temp file exists — not by `rename`'s accident; CI shows the guard
  `ok`. (If that check were removed, `rename` would refuse too: `MoveFileExW` → access denied, then std's retry with
  `FileRenameInfoEx`, flags `REPLACE_IF_EXISTS | POSIX_SEMANTICS` without `IGNORE_READONLY_ATTRIBUTE`, `windows.rs:1321-1390`
  — so the guard's Windows branch cannot tell the two apart; not a finding, the observable result is the same.)
- **The replace.** std 1.97's `rename` is `MoveFileExW(MOVEFILE_REPLACE_EXISTING)` first, falling back to
  `SetFileInformationByHandle(FileRenameInfoEx, REPLACE_IF_EXISTS | POSIX_SEMANTICS)` only on `ERROR_ACCESS_DENIED`.
  Same-volume `MoveFileExW` with replace is one metadata operation on NTFS; Microsoft documents no atomicity guarantee for
  it (read, not run). CI: `acw2_save_replaces_target_by_rename_and_leaves_no_temp` ok (a hard link keeps the old bytes).
- **`sync_dir`** (unchanged): `fs::File::open(dir)` on Windows opens without `FILE_FLAG_BACKUP_SEMANTICS` (std adds no such
  flag by default, `windows.rs:206-210,329-334`), so `CreateFileW` fails for a directory and `if let Ok(..)` skips the sync
  silently: no error, no sync. The module doc ("any failure … is ignored (unchecked on Windows, where opening a directory
  this way is expected to fail)") is true by this reading.
- **Shared code made reachable on Windows** (each T-074's by the spec; none makes a sentence of this task false, since
  `paths.md` now says the rules below "The root" are not stated for Windows): `std::path::absolute` on Windows normalises
  `..` lexically (`GetFullPathNameW`) while `canonicalize` resolves physically, so a `--root` with `link\..` may lead
  elsewhere at the first re-check → `OutsideRoot` (safe); junctions are `is_symlink()` (name-surrogate tags,
  `windows.rs:1197-1204`), their `\\?\`/`\??\` targets become `Step::Root` → `/` → the final `inside` check fails →
  `OutsideRoot` even for a junction inside the root (safe, wrong function); other reparse points (cloud files, dedup) are
  followed by the OS unnoticed (Q-6 B: T-074 refuses them); `RelPath` allows `:` so `f.txt:s` reaches an alternate
  stream and `C:x` makes `dir.join` drive-relative (the final `inside` check refuses the latter; the former is inside
  lexically); case-insensitive names and reserved names (with the `\\?\` prefix, `CON` is an ordinary name) are not
  treated. Backslashes are refused lexically (`paths.md` "Lexical refusals").
