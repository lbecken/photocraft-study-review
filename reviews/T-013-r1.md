**Design judgement: publish validates with a privately built main `xtask`.** Sound in intent: it
is the queue's trust rule (the validator is main's code, never the caller's binary), and it makes
step 1's would-be `docs/scorecard.md` come from the same build recipe the queue uses in step 8,
so the two cannot disagree. Its gain over the caller's binary is small in practice: step 1 already
requires a primary checkout equal to main apart from data inputs. The binary from `cargo xtask` is
therefore main's code too. The cost is one more compile of the xtask crate per publish, refusals
included (it runs before the scorecard checks). The real problem is where it builds: in the
queue's private tree, without the queue's lock (finding 3). Keep the design, and either take
the lock or build in `kiln-publish/`.
