### Questions from the brief
1. *Can a task weaken the gate that judges it?* `xtask/src`: no (main's binary; M01/M04 killed).
   The policy files `xtask/generated.toml`/`ledger.toml`: no (read from main, AC-16; M-tested by
   `config` tests). `.cargo/`, `rust-toolchain.toml`, `clippy.toml`, xtask data files: yes, both
   gates read the task's copy (F3, E1). Root `Cargo.toml`, `rustfmt.toml`, `build.rs`: not gate
   paths; covered only by `touches` + review (F3). Build scripts and tests can also poison the
   cached main binary for later runs (F1, E2). `Cargo.toml` aliases: aliases live in
   `.cargo/config.toml`; the queue does not use the alias (it runs the binary / `cargo run -p xtask`).
2. *`KILN_XTASK_RUN_IN`*: honoured only when it names the canonical workspace being run in
   (`provenance.rs:110`); inherited by gated task code, but the guard it relaxes is redundant on
   this path (F9). Accidental export in a director shell would excuse a stale binary only in
   exactly that directory.
3. *Vacuous prechecks*: empty `touches` allows only the task file, generated paths and (medium/high)
   test/review paths — not vacuous; `""`/`/` entries match nothing (`policy.rs:72-75`). Review
   without verdict → refused (`verdict ``). Approval for another task → refused (boundary check).
   Join record of another task or a non-`joined` result → ignored; an earlier round's record is
   accepted if its `joined_sha` is an ancestor (as specified); uncommitted/fake records accepted
   (F8). Stale review: caught for a hex sha (M13 killed), not for a symbolic `reviewed_sha` (F2).
   Front matter: only raw equality with main or with the merge base (D-019 a).
4. *Regeneration*: only all-generated conflicts are resolved (M07 killed); main's lock is restored
   before `cargo update --workspace` and version changes fail the run — but that is untested
   end-to-end (F5), and an un-conflicted task `Cargo.lock` change is never checked (F4). A task's
   intended lock pin is dropped silently on conflict (the gate then judges the regenerated lock).
5. *Seeding*: no stale artifact found. Member units are never copied; non-member path-dependency
   sources get the source mtime only when byte-identical (`seed.rs:178-216`), so cargo's
   mtime-vs-dep-info rule rebuilds anything that differs; a file not in the copied dep-info keeps
   its fresh checkout mtime (rebuild, never stale). E6 confirms for a changed path dependency.
6. *Side effects*: refusals leave main, branch, both statuses and `queue.jsonl` unchanged (AC-9,
   E4). Failures: `conflict` (rebase abort / `restore`) leaves the branch; `gate_failed` and
   `ff_failed` leave it rebased (F7); a record is written, as specified.
