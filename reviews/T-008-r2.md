## The held handle (task item 2)
- `disk.rs`:161 opens the canonical root (`fs::File::open(&resolved).ok()`); :163–166 take
  `root_id` from the handle's own `metadata()` when there is one, else from the construction-time
  `fs::metadata(root)`. The field `_root_handle` (:102) is never read: `grep` finds it only at its
  declaration and at :170. `current_root` (:189–198) resolves `given` with `fs::canonicalize` and
  compares (dev, ino) of the result; `locate` starts from that path. Nothing is resolved through
  the handle. VERIFIED by reading and by mutant `idfrommeta` (identity from `meta` instead of the
  handle: equivalent outside a race during construction).
- The stated limit is real: as `nobody` with a 0311 root, `File::open` fails (EACCES), no handle
  is kept, and probe (i) read `fresh/secret.txt` and wrote `fresh/f.txt` in 6 of 6 runs. As root
  (the test suite's user) the case cannot arise, because root bypasses the permission; I could test
  it only by dropping privileges with `setpriv`. Not tested: a root unreadable by ACL or LSM
  policy, network file systems.
- Judgement. Refusing such a root at construction would contradict the Interface pin "`DiskFs::new`
  returns the same `Ok`/`Err` values as today for every root"; refusing every later request when
  no handle is held would change today's behaviour of an unreadable root as well. Both need a
  ruling. The case is rare (a project root its own user cannot list) and needs another process to
  remove and replace the root between two requests. I judge the limit **acceptable for this task
  if documented**; but `docs/protocol/paths.md` does not document it at all, which v9 requires
  (R2-D1). Whether to close it (for example by opening the root with Linux `O_PATH`, which needs
  no read permission, or by refusing such a root at construction) is a follow-up for the director.
