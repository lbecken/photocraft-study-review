### `read_bytes` (three T-036 files)
- As uid 0, `fs::read` succeeds and nothing changes. As an ordinary user, `PermissionDenied`
  triggers `chmod(mode | 0400)`, one read, `chmod(mode)`, and then `unwrap`. The mode is restored
  before the result is unwrapped, so a failed second read leaves no mode changed. If either chmod
  fails, it panics (`set_mode` unwraps), which fails the test and never passes it.
- It cannot hide a product fault. `snapshot` records type, link target and bytes, never modes,
  before and after; the base did the same. The callers run it only while no request is being
  handled. In `acceptance_t036_cli.rs:387,432` and `acceptance_t036_workspace.rs:357,397` every
  child has exited. In `guard_t036_removal_cli.rs:487` a `kiln-cli control` session is alive but
  idle between requests, and its root is `root/`, not `open/` where the mode-0000 file lives. The
  negative control that proves U cannot read `locked.txt` (`acceptance_t036_cli.rs:366-383`,
  `guard_t036_removal_cli.rs:416-423`) runs before the first snapshot. The base already failed as
  uid 1000, so no previously passing check got weaker.

### `assert_reachable` (six files)
- It runs only when the child is dropped to 65534. `must_reach` is gated on `self.drop`, which is
  true only when a file the test just created is owned by uid 0. In `confinement.rs` it sits inside
  `if euid == 0`. It can add a failure and never a pass: it either panics or returns, and the test
  then runs unchanged.
- Its class choice (owner, else primary gid, else other) is the kernel's, for a child with no
  supplementary groups. Rust's `Command::uid` from uid 0 calls `setgroups(0)` when no groups are
  set. It checks every component of the canonical path, including `/` and the target itself (the
  x bit on the binary).
- Where it could pass while the child still cannot run, the test fails at spawn or at the positive
  control instead. Where it could fail while the child could run, the cause is ACLs (Finding 1).
