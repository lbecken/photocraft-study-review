    `real/sub/../../locked`): `locklink -> locked`, an absolute link to it,
    `real/sub/../../locked`, `./locked`, the absolute path;

  - below a 0700 root-owned ancestor, `hidden/inner` is refused with `Permission denied` from
    `metadata`, as on base.
  - default root: `cwd` of mode 0311 refused, naming ``root `.` ``, for `exec` and `control`.
- **Nothing runs or is created on a refused start.**
  - `run no-such.jsonl --root locklink` gives the `bad --root` line, not a script error.
  - `sleep 3 | control --root locklink` exits 2 at once without reading stdin.
  - `run s.jsonl --root locked --log l.jsonl` leaves an existing `l.jsonl` holding `keep`, and
    creates no new log file.
  - `find -newer` over the fixtures shows no new entry (and no `.kiln-tmp-*`).
  - `exec doc.open '{' --root locked` reports `invalid_json` first, as
    `docs/protocol/cli-memory-seed.md`:91–93 documents (see nit 2).
- **The handle.** `/proc/<pid>/fd` of a `control --root real` session shows
  `3 -> /tmp/t036-review-r192/docs/real`. The root is held, and only fds 0–3 are open.
- **Permission changed after start** (65534; root 0711 at start, then `chmod`):
  - 0311: `doc.open g.txt` and `doc.open sub/h.txt` ok; `project.tree {}` and `{"path":"sub"}`
    give `io_error` (``cannot list the project: (root): I/O error: Permission denied``);
    `doc.save` ok, writing `root/f.txt`;
  - 0000 and 0644: every request gives `io_error`, and the save writes nothing;
  - then the root removed and replaced: every request gives `outside_root` (AC-2 row).
  - This makes `docs/protocol/project.md`:110–111 ("a directory … that cannot be read … makes
    the whole command fail with `io_error`") true for a root made unreadable after start (the
    case Pinned (f) left INFERRED).
- **Held read-only roots replaced** (65534, 0644 and 0400): removed and replaced by a link to a
  new directory of the same mode. `project.tree {}` and `doc.open secret.txt` give
  `outside_root`; no reuse within 64.
- **Does holding change behaviour for readable roots?** No. Base already held every readable
  root (`File::open(..).ok()`, `git show 138be41:crates/kiln-workspace/src/disk.rs`). A held
  root that is removed with nothing in its place still gives `outside_root` (`removed-held`).
  - The one visible effect of holding: a root that is itself a mount point cannot be unmounted
    plainly while a session runs (`umount: … target is busy`).
  - After `umount -l`, the root path reaches the directory underneath, and every request gives
    `outside_root`.
  - This is not new for readable roots.
- **Could an accepted root be made to work in a replacement?** I found no way.
  - Every replacement I could make is a different (device, inode), and the held handle keeps the
    old inode allocated: link, new directory, file, bind mount over the path, lazy unmount,
    rename-and-replace, five cycles.
  - The only sessions that kept working are those whose root path still leads to the same
    directory. That is the documented "moved back / link pointed at it" case (the
    `renamed-linked-back` and `cycles` probes).
  - Not tried: a same-inode directory on another device (TG-2, accepted); an ACL or LSM denial
    (no `setfacl` on this machine).
- **EMFILE on the root open** could not be produced through the binary. With `ulimit -n 3` the
  dynamic loader fails (`libgcc_s.so.1 … Error 24`). With 4, the root open succeeds and the file
  open fails (`io_error`, `Too many open files`). That the open's own kind is passed through is
  checked by code reading only (`disk.rs`:181–182).
